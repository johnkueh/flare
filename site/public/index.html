What's in it

Three pieces, one Worker.

Use one or all three. Each is a small package you add to a Worker you already run.

Sync

Every phone keeps its own copy in SQLite and writes instantly. Phones share a space with an 8-letter invite code, and edits merge field by field, so nothing gets lost.

How sync works →

Auth

Every install is signed in from its first launch and proves it's a real copy of your app with App Attest or Android key attestation. Add a real account later and nothing is lost.

How auth works →

Analytics

Events queue on the phone, survive a crash or a day offline, and land in Cloudflare Basin as a table you query with SQL. No Firebase, no GA4.

How analytics works →
Merges that make sense

Two people edit at once. Both edits stay.

Your data is collections of JSON documents. Say what each field is, and Flare knows how to merge it.

value

Names, checkboxes, amounts. The newest edit wins.

position

Order in a list. Moving an item writes one field.

parent

Folders and nesting. Loops are refused.

set

Tags and members. Adds and removes from every phone survive.

counter

Counts every phone adds to. No increment is lost.

blob

Photos and files, kept in R2 and checked by hash.

How it's built

One Rust core. Your own Worker.

Your appSwift or Kotlin over the Rust core, with SQLite on the phone
Your WorkerSync, auth and events, on your Cloudflare account
CloudflareDurable Objects, R2, D1 and Basin

Built like Firefox's sync

It's the same approach Mozilla uses for Firefox on iOS and Android: the logic is written once in Rust, and UniFFI, Mozilla's binding generator, turns it into Swift and Kotlin. One set of merge rules, one set of tests, every platform.

Merges like Figma and Linear

Not a text CRDT like Yjs. Every field is its own value and the newest edit wins, lists use fractional indexing, and the server refuses loops in nested items. It's the model Figma's multiplayer and Linear's sync engine are built on. How conflicts resolve

Cheap, and nothing to babysit

One Durable Object per space, photos in R2, accounts in D1. Analytics at small-app volume costs nothing beyond Workers Paid. No servers, no database to run.

Add it

Add it to the stack you already have.

pnpm add "@sync/server@github:johnkueh/flare#0.2.0&path:/server"
pnpm add "@flare/auth@github:johnkueh/flare#0.2.0&path:/auth"   # accounts
// src/index.ts
export { SpaceObject } from "@sync/server/space";

Add the package https://github.com/johnkueh/flare and link SyncKit and SyncClient. Then describe your data and open the store:

let store = try SyncStore.open(path: dbPath, schemaJson: """
  {"groceries": {"name": "value", "done": "value", "position": "position"}}
""")
try store.putDoc(collection: "groceries", doc: id, fieldsJson: #"{"name":"Milk","done":false}"#)
let rows = try store.list(collection: "groceries", orderBy: "position")
// settings.gradle.kts
maven("https://jitpack.io")
maven("https://pub-796846793f3e431ab3a92e0577c57dde.r2.dev/maven")

// app/build.gradle.kts
implementation("com.github.johnkueh:flare:0.2.0")

A web page doesn't run the Rust store. Its own Worker reads and writes through SyncGateway over a service binding, which never leaves your account.

// the API Worker
export { SpaceObject } from "@sync/server/space";
export { SyncGateway } from "@sync/server/gateway";

// the web Worker's wrangler.jsonc
"services": [{ "binding": "SYNC", "service": "my-api", "entrypoint": "SyncGateway" }]
